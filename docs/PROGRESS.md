### 授权与发码（2026-10-08）

离线授权已实现：默认 30 天试用，到期后 Start 仍可点（点击弹激活窗、任务被拒），
可进界面不能跑任务；
激活码用 Ed25519 签名（122 字符），绑主板 UUID + CPU ID。

- 模块：`src/rok_assistant/infra/licensing/`（`codec` / `verify` / `pubkey` /
  `fingerprint` / `store` / `state` / `guard`）。**`guard` 是唯一门面**：
  界面只认它，闸门在 `GuiController.start()` 与 `MainWindow._on_start()`；
  worker 完全不碰授权——它们是被闸门放行之后才起来的。
- 存储三处冗余（注册表 + `C:\ProgramData` + `<user_dir>\.roklicense`），
  **重新解压只清得掉第三处**——这就是防「解压刷新试用期」的全部机制。
- 到期日**不落盘**，每次启动从记录里的签名码现算，所以伪造它需要私钥。
- **时钟回拨不判篡改**（2026-11-01 改）：只剩 `effective_now = max(now, last_seen)`
  + 「`last_seen` 只增」这一条「不给好处」。原先那两条判死（回拨超 24h / 文件
  mtime 在将来）已删——它们对防作弊没有额外贡献（到期日是绝对日期），只会把
  误调时间的用户永久锁死：调到未来 → 激活 → 改回正确时间 → 判回拨 = 篡改 →
  「激活成功但状态仍 expired」，连再买一张码都救不回来。
  判篡改现在只剩**一条**路径：记录结构完整但 HMAC 验不过（= 改坏记录）。
- **重输已用过的码不再报错**（2026-11-01 改）：`verify` 只剩**三步**校验（解码 /
  验签 / 比对本机），第四步「serial 未用过」取消——防重放靠 `apply_activation`
  的幂等（同一个 serial 加不上第二次时间），做成报错只会让已授权的用户重输时
  看到「该激活码已被使用」，误以为码作废。激活窗现在把**结果状态**一并显示
  （「激活成功（当前：已授权，剩余 30 天）」），避免「激活成功但仍是 expired」这类
  骗人的提示。
- 设计文档：`docs/superpowers/specs/2026-10-08-授权与发码平台-design.md`
  （§12 列了 **8** 条**已知局限**，别当成没实现）

13. **运行过一次就删不掉解压出来的文件夹**（10-11 用户报，**已修**）。
    用户原话：「是有什么隐藏的后台运行程序吗」——**有，但不是我们的**。
    绿色包是解压即用、双击 exe 启动的，所以 app 进程的 CWD **就是解压目录**；
    子进程默认继承它，而 adb 客户端在本地没有 adb server 时会 fork 出一个
    **常驻**的 `adb -L tcp:5037 fork-server server`，把客户端的工作目录句柄
    一起继承下去。Windows 不允许删除任何活进程还开着的目录，于是 app 退出后
    文件夹照样删不掉。**任务管理器里找不到 `rok-assistant.exe`**，所以看起来
    像「隐藏的后台程序」。
    **已排除的**（别再走一遍）：app 自己残留进程——把 `dist/rok-assistant`
    整包复制成「解压目录」、按双击的方式（CWD = exe 目录）跑
    `rok-assistant.exe --selftest`，10s 退出、rc=0、13/13 通过、零残留进程，
    之后那个目录**当场可删**；也扫过全机所有进程的 CWD（读 PEB），没有任何
    进程的工作目录指向用户目录。
    **机制**：`_probe_cwdfix.py` 做 A/B 对照——A 子进程继承 app 的 CWD →
    `PermissionError: 另一个程序正在使用此文件`，`adb kill-server` 后立刻可删；
    B 给子进程指定中性 CWD → 当场可删。
    **修法**：`infra/subproc.run` 加 `cwd=neutral_cwd()`（系统临时目录；**不能
    指 app 目录的子目录**，子目录被钉住父目录一样删不掉）。`test_subproc.py`
    三条测试钉着，其中一条**真起一个进程问它的 `os.getcwd()`**——spy 只能证明
    我们传了 `cwd`，证明不了 CreateProcess 照做了。
    **副作用已测**：守护进程钉在临时目录上，Temp 里的文件/子目录照常增删。
    **已经踩上的用户**：任务管理器结束 `adb.exe`（或 `adb kill-server`）后即可
    删除，不用重启；MuMu 会自己再把 adb 拉起来。

14. **「弹窗关不掉 / 寨子打不了」把一次卡顿升级成停机**（10-12 用户报，**已修**，
    **实机复验待补**）。两条一起报的：①体力不足 → 能自主加体力 → 卡在体力界面
    不再有后续动作 → 一直重试 → **最后失败退出程序**（追问确认「弹窗压根关不掉，
    程序还在反复点」）；②搜到的寨子被其他玩家集结 → 蓝色集结框不弹 → 一直卡在
    这一座，直到它消失才重新发起。
    **根因**（证据在 HISTORY 同日一节）：关弹窗没有独立证据（点一次 X 就当关了，
    而 `ap_refill` 的 ROI 只有标题窄带，一次失配就误判）；补不动一律**抛异常**，
    而 `WorkerRunner` 异常时**不重建 SM**——只在同一状态退避重放，攒满
    `max_consecutive_failures*2 = 6` 次异常就停机；`_verify_unlocked` 把「蓝框
    没弹」**一律**归因「被别人集结」，`_click_red_rally` 的点击结果被丢掉；
    恢复动作点一下空地就走，没有任何一步确认详情**真的**收掉了（`red_rally`
    与 `search_icon` 的 ROI 不重叠，NORMALIZE 不会替我们收）。
    **修法**：见「已落地」表 10-12 一行。核心是把「卡死」改成本轮**干净中止**
    （`fail_reason` + 对应 END 边）交冷却后的下一轮，并给每个「关掉了没」补上
    `_wait_for_gone` 式的**验证**。
    **下次实机先看这三句日志**：`补行动力：… 弹窗仍在场`、
    `蓝色集结框未出现（第 N/5 次，原因=…）`、`城寨详情弹窗收不掉（red_rally 仍在场）`。

### 实机运行手册

**Step 0 — 起模拟器并确认实例真的起来了。** 只有 MuMu 启动器窗口 ≠ 实例在跑：


**adb server 没起**，不是模拟器没起：

```bash
ADB=C:/模拟器/MuMuPlayer/nx_main/adb.exe
"$ADB" kill-server; "$ADB" start-server
"$ADB" devices                    # 手动排查时才需要 connect
```

**Step 1 — 两号都登录并停在地图视图。** 这是唯一必须手工做的：归一化靠 `search_icon`/`alliance_btn`
认地图，停在登录页/活动弹窗会让门槛在 unknown 上白等 900s。截图确认是 1920×1080（不是竖屏）：

```bash
"$ADB" -s 127.0.0.1:16416 exec-out screencap -p > _probe1.png
```

**Step 2 — 核对配置。** 读 `config.yaml` 确认：各号 `target_levels` 的寨子搜得出来（搜空会连续计失败）、
`fill_target_leaders` 互相指向、`role` 取值合法。**文档不记具体配置值，以 `config.yaml` 为准。**

**Step 3 — 启动驱动**：见上面速查（必须 `nohup` 脱离式）。点 Start 会先自动预检每台模拟器
