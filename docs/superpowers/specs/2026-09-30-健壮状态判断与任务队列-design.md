# 健壮状态判断 + 任务队列 —— 设计

> 2026-09-30。经 brainstorming 三节逐节确认（任务/消息层 → 判据层 → 断点续跑/测试）。
> 上游设计：`docs/superpowers/specs/2026-07-15-rok-assistant-design.md`。

## 一、问题：中断的实证清单

从全部实机日志（`_driver.log`、`_goal_run*.log`）统计，中断原因分布如下：

| 原因 | 次数 | 性质 |
|---|---|---|
| `no_rally_found` | **42** | 填兵方在战争列表里找不到车头的集结 |
| 门槛判「队列图标不可辨」 | **166** | 门槛长期停在 `unknown` |
| step 异常 `search_icon 不可见且 map_btn 归一化失败` | 12 | 视图状态判错 |
| step 异常 `联盟旗帜不可见：既不在地图视图，退搜索也没找到` | 9 | 视图状态判错 |
| step 异常 `march_btn 不可见` | 5 | 视图状态判错 |
| 门槛告警「未知队列图标已持续 900.0s」放行 | 9 | 计时器赌判据 |
| `no_fortress_found` | 3 | 搜不到符合等级的寨子 |
| `rally_rejected` | 2 | 开车被游戏静默拒绝（本应降级，未生效） |
| `locked_fortress` | 1 | 寨子被锁定 |

三类根因：

1. **通信靠猜**。填兵方靠"打开战争列表按名字找行"推断车头是否已发车；车头靠进程级
   `RallyEventTracker` 的 480s 窗口推断对方是否已发车。**已知事实被退化成猜测**，
   `no_rally_found` 42 次是它的直接代价。
2. **判据靠单帧像素**。所有状态都从画面反推；一帧看不清就落 `unknown`，再用
   `_QUEUE_UNKNOWN_GRACE=900s` 计时器放行。166 次 `unknown` 说明判据本身不可靠，
   计时器只是给不可靠判据加了个定时炸弹（9 次放行 → 可能对应 `rally_rejected`）。
3. **恢复粒度太粗**。任何逻辑失败 → `is_terminal()` → runner 重建**全新 SM**，
   排队中的填兵任务一起丢。一步失败作废整轮。

### 核心洞察

系统把"我知道的事"也当成"要猜的事"：我自己发的车、我自己填的兵、对方刚发来的通知，
这些都是**已知**，却都退化成了读队列栏猜。按**可信度分级**（账本 → 消息 → 画面）
能一次性消掉前两类。

## 二、目标与非目标

### 目标

- 车头与填兵方**直接通信**，取代所有基于像素/登记的推断
- 集结流程与填兵流程作为**队列**运行：集结流程不可抢占，填兵任务排队等待
- 中断时可**从断点续跑**，不必整轮重来
- "何时搜索寨子 / 何时允许发起集结"的判据**可解释**：说不清就说明为什么说不清

### 非目标（本次明确不做）

- **不重写为 `Task([Step...])` 模型**。现有 `EitherStateMachine` 的 state 已是步骤粒度，
  复用即可；全面重写要动 423 条测试里的一大部分，且当前正跑验收，风险不对等。
- **不做反向通道**（填兵方 → 车头「我填完了」）。车头的 `WAIT_RETURN` 等的是
  **自己部队回城**，填兵方的消息帮不上，加了就是一条没人消费的消息。
- **不做排序激活项判据**（沿用 09-29 方案的结论：只画条和下拉，不声称哪一行激活）。
- **不动 `templates:` 的 `preset_1..6` 阈值与共享 ROI**。

## 三、架构：四层

```
┌─ 任务层   TaskQueue：RallyTask（不可抢占） / FillTask（排队 + TTL）
├─ 消息层   Mailbox（每线程一个收件箱）+ MailRouter（按收件方配置过滤投递）
├─ 判据层   L0 账本/消息  →  L1 画面多帧投票  →  L2 ViewProbe 视图判定
└─ 恢复层   步骤失败原地重试 → 预算耗尽只作废当前任务
```

依赖方向：`coordination/` 提供 TaskQueue 与 Mailbox；`workers/` 消费。**不反向依赖**。

## 四、任务层

新增 `coordination/task_queue.py`：薄类，`push(task)` / `peek()` / `pop()` / `busy`，
线程安全。

`EitherStateMachine` 持有队列，`step()` 按队头分派：

```
step()
  ├─ 队头 RallyTask 未开始 → 开始（_phase="leader"），标记 running
  ├─ 队头 FillTask 未开始 → 仅当无 RallyTask 在跑 → 开始（_phase="member"）
  └─ 任务终态 → pop；队列空 → _phase="done"，交回 runner
```

**唯一抢占规则**：`RallyTask` 一旦开始不可抢占。这直接实现"收到通知先判断是否还在
集结流程中，要等集结流程完毕才可以转入填兵流程"——从"避免撞车"变成"结构上不会
被打断"。

### FillTask 的 TTL

```python
_FILL_TASK_TTL = 240.0   # 4 分钟
```

语义：**计时从消息入队起，条件是"仍未进入填兵流程"**。

- 每次 SM 决定下一步前检查队头 FillTask：`now - msg.ts > TTL` 且**尚未开始** → 丢弃
- **已开始执行的填兵流程不受 TTL 影响**——进了流程就走完，否则会在点了一半的位置被丢弃
- 丢弃必须记日志：`[填兵] 任务过期丢弃（等待 Ns 未轮到）`。排队 4 分钟没轮到说明
  本地集结流程超时了，那本身是要看的信号

## 五、消息层

新增 `coordination/mailbox.py`：每线程一个收件箱（`deque` + `Lock`），`post()` / `drain()`。

```python
@dataclass(frozen=True)
class RallyLaunchedMsg:
    leader_char_id: str      # 投递过滤用
    leader_char_name: str    # 填兵方按它在战争列表定位那一行
    target_level: int
    ts: float                # TTL 用
```

**投递路径**：`MailRouter` 订阅一次 `rally_launched`，**按每个收件线程自己的
`fill_target_leaders` 过滤后**投进它的 Mailbox。过滤逻辑放在收件方——投递方不需要
知道谁填谁，配置耦合只在一个方向。

**删除**：`RallyEventTracker`、`_LEAD_JITTER_MAX`（45s 错峰抖动）。
抖动是"碰运气不撞车"，登记簿是"从像素/时间推断对方状态"，两者都被定向消息取代。

## 六、判据层

### L0 —— 准入判据（不读画面）

"何时允许发起集结"由已知事实决定：

1. **本地账本**：我自己的部队不在外（我发的车已回城 / 我没在填兵）
2. **对方消息**：Mailbox 里没有未过期的、来自"我该填的人"的 `rally_launched`
   —— 有则**准备**转填兵，但仍要先跑完本地集结流程
3. 两号各自独立判断、**可同时开车**。不存在"一轮只能一个车头"的约束

#### 账本必须进程级：`ActionLedger`

账本记的是"我自己做过什么"，**不能挂在 SM 上**——runner 在每次终态后会重建 SM
（第七节只保证*任务*粒度不重置，整轮终态仍会重建）。账本若随 SM 死，L0 就退化成
"每轮开头一律认为部队在家"，正好把 `rally_rejected` 又放回来。

新增 `coordination/action_ledger.py`：按 `char_id` 记录，进程级，生命周期与
被删除的 `RallyEventTracker` 相同（后者当初做成进程级也正是这个原因）。

```python
@dataclass
class ActionLedger:
    troops_out: bool = False          # 我是否有部队在城外
    troops_out_since: float = 0.0     # 用于判断"在外太久"（异常信号）
    last_rally_launched_ts: float = 0.0
    last_fill_ts: float = 0.0
```

**写入点（SM 显式写，不猜）**：

| 时机 | 写入 |
|---|---|
| 行军点击确认成功（车头发车 / 填兵行军） | `troops_out=True`, `troops_out_since=now` |
| `WAIT_RETURN` 判定队列已空（部队回城） | `troops_out=False` |
| 发车确认 | `last_rally_launched_ts=now` |
| 填兵流程完成 | `last_fill_ts=now` |

**读取点**：L0 准入、L1 的 unknown 覆盖、`WAIT_RETURN` 的超时归因。

**约束**：账本只在**确认动作已生效**时写入。写不进去（点击未确认）就不写——
账本的价值全在"它是已知事实"，一旦掺入猜测就退化回像素判据。

### L0 补充：`rally_rejected` 由消息驱动降级

`runtime.py` 注释里记着本该降级（"自己被拒且窗内对方确有集结 → 竞态输家轮空不计失败"），
但靠 480s 窗口去猜，**未生效**（今天实测 2 次被计为失败）。改为精确判定：

```
开车被拒 + Mailbox 里有未过期的对方 rally_launched
  → 判为竞态输家：不计失败，不消耗连续失败额度，转填兵
开车被拒 + 无任何对方消息
  → 真失败，照旧计数
```

### L1 —— 画面判据：多帧投票 + 账本覆盖

队列栏判据现在**单帧采信**，是 166 次 `unknown` 的结构性原因。

- **连续 3 帧同结论才生效**（N 可配）。对 `queue_flag_icon` 这种 0.758 稳定读数
  投票不会让它变好——**阈值/模板该修还得修**（见"遗留"节）——但能干掉"偶发一帧噪声
  导致整轮判错"
- **三帧不一致时的规则**（必须明确，否则又是歧义）：维护最近 N 帧结论的滑动窗口，
  仅当窗口内**全部相同**才采信并更新"当前判据值"；否则**维持上一次采信值**，
  窗口滑动继续攒。若从未采信过（进程刚起）则落 `unknown`。
  即：投票只会**延迟**结论，不会**翻转**结论——避免"噪声把 battle 翻成 none 然后放行"
- 帧间隔沿用现有的判据轮询间隔（1s），不额外加采样

**为什么这条重要**：`battle`（阻塞）与 `none`（放行）之间的误判是**有方向性代价**的
——把 battle 误判成 none 会开一次注定被拒的车（今天 2 次 `rally_rejected` 的形态），
反过来只是多等几拍。滑动窗口"只延迟不翻转"的选择，正是在这个不对称上取的安全侧。
- **unknown 不再靠计时器放行**，改为**问账本**：
  - 账本说我部队在外 → 继续等
  - 账本说我不在外 → 放行
  - `_QUEUE_UNKNOWN_GRACE=900s` **降级为最后兜底**（防账本本身出错）
- 目标：消掉那 9 次"未知队列图标已持续 900.0s"告警放行

### L2 —— 视图判据：ViewProbe

`search_icon 不可见且 map_btn 归一化失败`(12) / `联盟旗帜不可见`(9) / `march_btn 不可见`(5)
——都是"不知道自己在哪个视图"，只能靠"点一下再看某模板在不在"盲试。

新增 `ViewProbe`：一次截屏判定当前视图 + 置信度：

```
{地图, 城市, 战争列表, 搜索面板, 集结弹窗, 创建部队, 弹窗遮罩}
```

判据锚点（沿用既有模板）：

| 视图 | 锚点 |
|---|---|
| 地图 | `search_icon` 或 `alliance_btn` |
| 城市 | `map_btn`（进入城市城堡按钮） |
| 战争列表 | `war_title` |
| 搜索面板 | `search_back` / `search_btn` |
| 集结弹窗 | `rally_attack_popup` |
| 创建部队 | `form_title` / `march_btn` |
| 弹窗遮罩 | `replace_popup` / `ap_refill` / `warning_panel` / `menu_expanded` |

归一化从"点 `map_btn` 再赌 `search_icon` 出现"变成**从当前视图到地图的已知路径**。
失败信息从 `search_icon 不可见` 变成 `卡在[创建部队]视图，遮罩未关`。

## 七、恢复层：断点续跑

现在只有**一种粒度**：任何逻辑失败 → `ctx["failed"]` → `is_terminal()` 为真 →
runner 记一轮、冷却 30s、**重建全新 SM**，排队任务一起丢。拆成两级：

### ① 步骤失败 → 原地重试，不回退 state

`step()` 失败时不重置 `current`，只给该 state 的失败计数 +1，下次仍从同一 state 尝试。
预算 `_STEP_ATTEMPTS = 3`（**每 state 独立计数，该 state 成功推进时清零**）。

**这需要改 `StateMachine.step()` 的推进语义**。现状是：跑完 action **无条件**
`self.current = t.to_state`——也就是说一个"点了但没生效"的 action 会静默推进，
错误被推迟到下一个 state 才以"前置条件不满足"的形式爆出来（日志里那 26 次视图判错
多半是这么来的）。改为：

| action 的结果 | 行为 |
|---|---|
| 正常返回 | 推进到 `t.to_state`，该 state 计数清零 |
| 返回 `False` | **不推进**，该 state 失败计数 +1 |
| 抛异常 | **不推进**，失败计数 +1，同时沿用 runner 现有退避重试 |

`False` 是"这一步的已完成判据没达成"的显式信号——比如 `_confirm_search` 点了
`search_btn` 但没等到结果面板出现。它让失败**当场归因到出错的 state**，
而不是漂到下游变成 `search_icon 不可见`。

前提是 action **重试安全**。规则：**每个 state 的 action 必须先评估"已完成判据"、
只做差量动作**。这不是新发明——`_select_level` 已经是这个模式（缓存差量，只在需要时
点 N 下）。推广到其余 state 即可。

少数做不到的（如 `_click_red_rally`，点下去才知道结果），重试前先跑一次 `_resync()`：
关掉所有已知残留面板 + 回地图视图。这一步由 L2 的 `ViewProbe` 支撑，两节在此咬合。

### ② 步骤预算耗尽 → 只作废当前任务，不重置 SM

作废 RallyTask，但**保留账本**（部队在不在外、Mailbox 里还有什么），然后继续执行
排队的 FillTask。这是关键改动：现在"搜寨失败"会把整轮连同待填的兵一起丢掉。

### runner 语义随之调整

"一轮"的定义从"一次 SM 生命周期"变成**"清空一次队列"**：

- `rounds_done += 1` 在队列清空时
- `fail_streak += 1` **仅当本轮一个任务都没成功**

RallyTask 失败但 FillTask 成功 = "干成了活的一轮"，不消耗连续失败额度。
"连续 3 轮失败停机"因此仍只在真·体力耗尽时触发。

今天那 2 次 `rally_rejected` 在新语义下：被拒 → 有对方消息 → 降级 → 转填兵成功
→ **本轮算成功**。

## 八、配置变更

1. **两号配不同 `target_level`**（8 级实测刷不出寨子，故为 7 ⇄ 6 这类组合）。
   等级不同 → 搜索目标不同 → **不会搜到同一个寨子**，这是删除 `_FOREIGN_RALLY_WINDOW`
   的前提。
2. **删除 `_FOREIGN_RALLY_WINDOW = 480.0`** 及其"对方已发起 → 本轮不搜直接填"分支。
   既然同时开车是允许的，用"不发车"规避一次**已降级**的失败，代价（少练一次车头 +
   少一次互填机会）大于收益。
3. **新增启动期校验**：两个 `role ∈ {leader, either}` 的角色 `target_level` 相同、
   且互为对方 `fill_target_leaders` 时，打 WARNING：

   > `[配置] 两号同为 N 级且互为填兵目标：可能搜到同一寨子，撞车时后发者被静默拒绝`
   > `（已降级不计失败，但白烧一次搜索）。建议配置不同等级。`

   只告警、不拦启动。价值在于：配置哪天漂了，启动日志里就有答案，不必去翻 run11 的旧账。

## 十、实施顺序与拆分（风险递增）

1. **L1 多帧投票 + 账本覆盖 unknown** —— 最便宜，直接消 166 次 unknown
2. **L2 `ViewProbe`** —— 消 26 次视图判错，并给 `_resync` 提供支撑
3. **任务层 + 消息层 + TTL** —— 消 42 次 `no_rally_found`
4. **断点续跑 + runner 语义** —— 改动面最大，放最后
5. **配置改不同等级 + 启动告警** —— 一行配置 + 一个小校验

### 拆成两个实施计划

本 spec 跨两个**互相独立**的子系统，风险profile 不同，因此**不写成一个大计划**：

| 计划 | 含步骤 | 性质 | 可独立交付 |
|---|---|---|---|
| **A：判据层** | 1、2、5 | 不改架构，只加判据与校验 | ✅ 做完即可实机跑，收益立现（166+26 次中断） |
| **B：任务队列 + 消息 + 断点续跑** | 3、4 | 架构改动，动 `either_sm`/`runner` 核心 | ✅ 依赖 A 的 `ViewProbe`（`_resync` 用）与 `ActionLedger` |

计划 A 先做且独立可验收；计划 B 在 A 合入后再起。两者的唯一耦合是
`ActionLedger`（A 引入并用于 L1 覆盖，B 复用）与 `ViewProbe`（B 的 `_resync` 调用）。

`ActionLedger` 因此归入**计划 A**。

## 十一、遗留（不在本次范围，但会继续造成中断）
