# 多模式框架与城寨等级扩展 —— 设计

> 日期：2026-10-13　状态：待实现
> 前置：`2026-10-13-企业级界面重构-design.md`（视觉层与设计令牌）、
> `2026-09-09-config-multi-instance-gui-design.md`（配置骨架）
> 相关：`docs/配置说明.md`（**随绿色包分发；本次配置结构变了，必须同步重写**）

## 1. 目标与由来

用户提了两条需求：

1. 城寨等级从 1–10 扩到 **1–15**；
2. 软件增加两个模式（**宝石模式**、**答题模式**，先做空白页待开发），
   当前模式命名为「**寨多多模式**」。

第 2 条在澄清过程中长成了**信息架构级的改动**：模式要有各自的配置、主界面要按
模式分页、每个模式各自一个「开始运行」按钮。所以本次实际交付的是
**多模式框架 + 城寨等级扩展**，不是"加两个下拉项"。

## 2. 已定决策

| 决策点 | 选择 | 影响 |
|---|---|---|
| 11–15 在哪 | 同一搜索面板，步进器上限提到 15 | 面板布局不变，只是上限 |
| 两区间关系 | **互斥**，不许混选 | 新增一条配置校验规则 |
| 盲降落到哪 | **本区间的下界**（1 或 11），不是固定 1 | 盲降次数按区间跨度算 |
| 区间怎么切 | 面板上有**独立的区间控件** | 新增两个模板识别条目 |
| 配置分区 | `app:` 公共 + `zhaiduo`/`gem`/`quiz` 各持 `instances` | 破坏性结构变更 |
| 界面版式 | **左侧导航 + 页内主按钮** | 顶部操作栏解散 |
| 模式是否落盘 | **不落盘**，固定开在寨多多 | `config.yaml` 里没有 `mode` 键 |
| 老配置怎么办 | **不迁移**，硬报错让用户重配 | 见 §5.2 的发布顺序约束 |
| 每角色等级数 | 保持 ≤ 3 | 不变 |
| 运行中切页 | **禁止**，锁导航 | 运行中只能看当前模式页 |

## 3. 架构

### 3.1 配置按模式分区

```yaml
app:                        # 公共：屏幕 / 路径 / 模型 / 反检测 / 收工阈值
  screen_width: 1920
  ...
zhaiduo:                    # 寨多多模式
  instances: [...]
gem:                        # 宝石模式（占位，可为空）
  instances: []
quiz:                       # 答题模式（占位，可为空）
  instances: []
```

`app:` 里的东西对所有模式一视同仁（分辨率、MuMu/adb 路径、检测模型、
反检测参数、收工阈值）；模拟器与角色配置**各模式一份**。

选这个分法的理由是 YAGNI：宝石/答题将来可能是完全不同的流程，现在猜
"它们会共用同一批模拟器"是投机。等真要共用时再把公共部分往上提一次即可。
代价（同一台模拟器将来可能要配三遍）现在不兑现。

### 3.2 模式是**界面**概念，不是运行时概念

`RuntimeCoordinator` 只跑寨多多——因为只有它被实现了。模式不进配置、
不进运行时签名，只决定**看哪一页**。

于是：

- `config.yaml` 里**没有** `mode` 键（早先设计过 `save_app_mode` 逐行回写
  配置以保住注释，那套机制连同它的复杂度**整个删掉**）；
- `RuntimeCoordinator` 的构造签名不变，只是内部读 `config.zhaiduo.instances`
  而不是 `config.instances`；
- 模式进入运行时的唯一入口是 `GuiController.start(mode)`，闸门放在那里。

### 3.3 等级区间是一等概念

1–10 与 11–15 不只是"数字范围"，而是**两个互斥的搜索区间**。这个概念同时
出现在三处，所以给它一个名字（`level_range(lv) -> (low, high)`）而不是在三处
各写一遍 `if lv > 10`：

| 出现的地方 | 用区间做什么 |
|---|---|
| `_check_levels` | 判定"混选了两个区间" |
| `_select_level` | 决定点哪个区间控件 |
| `_blind_set_level` | 决定降到底是 1 还是 11、点几次 |

## 4. 城寨等级 1–15

### 4.1 常量收拢（`infra/config.py`）

```python
MIN_TARGET_LEVEL = 1
MAX_TARGET_LEVEL = 15
RANGE_BOUNDARY = 10          # 1..10 | 11..15 的分界

def level_range(lv: int) -> tuple[int, int]:
    """该等级所属区间的 (下界, 上界)。"""
    return (MIN_TARGET_LEVEL, RANGE_BOUNDARY) if lv <= RANGE_BOUNDARY \
        else (RANGE_BOUNDARY + 1, MAX_TARGET_LEVEL)
```

`_check_levels` 改两处：范围校验改用常量；**新增区间互斥**——列表里同时出现
落在两个区间的值就报错。它和 `RAIDER_TARGET`（劫掠者寨子与等级互斥）是并列的
两条互斥规则。

### 4.2 切区间：灰态模板 + 幂等点击

`_select_level` 的顺序变成：点页签 → **切区间** → 读等级 → 点差量 → 回读校验。

切区间沿用仓库既有的**「灰态模板」惯用法**（`tab_fortress` / `tab_raider` 就是
这么写的）：模板只裁**未选中**态，命中 ⇔ 当前不在该区间 ⇔ 点它；已在目标区间
则不命中，`_click` 自动跳过。**幂等，不需要先读状态**——这一点很关键，因为
"当前在哪个区间"本来就不容易读准。

新增两个模板条目 `level_range_low` / `level_range_high`（PNG 需从实机截图采）。

识别器缺失时两种处理**不对称**，判据与 `tab_raider` 缺条目那次相同：

| 目标区间 | 识别器缺失 | 理由 |
|---|---|---|
| 11–15 | **抛异常**结束本轮 | 配置要 13、实际搜 8，属"静默搜错目标"，宁可按异常停机 |
| 1–10 | 只 warning，继续 | 旧模板包仍能用，行为与改动前一致 |

1–10 这一格留了个口子：若识别器缺失而面板实际停在 11–15 区间，会**搜错等级**。
之所以仍不抛异常，是因为它**不静默**——`_verify_level` 的回读值不在目标区间内
（§4.4），日志里会留下明确的 warning，最终由 `no_result` 计数自然兜住本轮。
这与既有的"等级回读未确认不烧一轮"是同一套哲学：环境类偏差不该升级成停机。

### 4.3 盲降降到**本区间的下界**

现有 `_LEVEL_BLIND_RESET = 12` 恰好等于 `(10 − 1) + 3`。改成按区间跨度推导：

```python
_LEVEL_BLIND_MARGIN = 3      # 余量：多点的几下打在滑条端点上，无害

def _blind_reset_clicks(target: int) -> int:
    low, high = level_range(target)
    return (high - low) + _LEVEL_BLIND_MARGIN
```

1–10 → **12 次（与现状逐字等价）**；11–15 → 7 次。
`_blind_set_level` 的起点从固定 `1` 改为区间的 `low`。

### 4.4 跨区间后等级缓存会失步（必须一并修掉）

`_LEVEL_CACHE` 存的是"面板当前等级"。切区间后滑条重置到 11，缓存里的 `8`
立刻变成谎话——`_blind_set_level` 会拿它当起点点 `+5`，落到 16。

两处加区间判断：

- `_blind_set_level` 的缓存命中条件加 `level_range(cached) == level_range(target)`，
  不满足即走盲降；
- `_verify_level` 的回读值若不在目标区间内，**直接判失败，不补点**
  （跨区间的差量点击没有意义）。

### 4.5 `_read_level` 的合法范围

`1 <= lv <= 10` → `MIN_TARGET_LEVEL <= lv <= MAX_TARGET_LEVEL`（判断与
warning 文案两处）。

### 4.6 配置界面

15 个复选框，5 列 × 3 行；第 2/3 行之间加一条弱分割线示意区间分界；
劫掠者行从 `(2, 0, 1, 5)` 移到 `(3, 0, 1, 5)`。

> **勘误（后补）**：上面的字面值 `(3, 0, 1, 5)` 已被推翻——第 2 行被两个区间
> 之间的视觉分隔线占用，所以 11–15 落在第 3 行，劫掠者行实际是
> `(4, 0, 1, 5)`（实现即按此落位）。本注即勘误，原值保留备查；照原值去改
> 代码会与分隔线撞行。

互斥做成**勾不到**而不是**报错**：勾 11–15 任一格 → 自动清空 1–10 的勾选，
反之亦然；与劫掠者三者两两互斥。沿用对话框里已有的
`_on_raider_toggle` / 超上限自动撤销勾选那套写法——**状态永远合法**比
"允许勾错再弹提示"轻。

## 5. 多模式

### 5.1 模型

```python
class AppMode(str, Enum):
    """值用于内部标识（ASCII），标签进界面。"""
    ZHAIDUO = "zhaiduo"
    GEM = "gem"
    QUIZ = "quiz"

MODE_LABELS = {AppMode.ZHAIDUO: "寨多多模式",
               AppMode.GEM: "宝石模式",
               AppMode.QUIZ: "答题模式"}

# 已实现的模式。加模式时从别处挪进来即可——这是"某个模式做完了"的唯一开关。
IMPLEMENTED_MODES = frozenset({AppMode.ZHAIDUO})
```

中文标签放 `infra/config.py` 而不是 `gui/labels.py`，跟 `RAIDER_LABEL` 走同一
先例：它同时被 GUI（导航项、按钮）和协调器（拒绝启动的报错）用到，跨层共用
的中文文案在本仓库放 config.py。

```python
class ModeConfig(BaseModel):
    """一个模式的专属配置。宝石/答题现在是空壳，故允许空。"""
    instances: list[InstanceConfig] = Field(default_factory=list)

class ZhaiduoConfig(ModeConfig):
    instances: list[InstanceConfig] = Field(min_length=1)
    # _cross_checks 整块从 RootConfig 搬到这里

class RootConfig(BaseModel):
    app: AppConfig = Field(default_factory=AppConfig)
    zhaiduo: ZhaiduoConfig
    gem: ModeConfig = Field(default_factory=ModeConfig)
    quiz: ModeConfig = Field(default_factory=ModeConfig)

    def instances_for(self, mode: AppMode) -> list[InstanceConfig]:
        return getattr(self, mode.value).instances
```

**校验跟着数据走，不跟着模式走**：`_cross_checks`（实例 id 不重 / 角色 id 不重 /
至少 1 个 leader 或 either / 填兵目标互相指向 / leader 不许配填兵目标）整块搬到
`ZhaiduoConfig`。宝石/答题现在没有角色，硬套"至少一个 leader"会当场加载失败。

### 5.2 硬断：不做迁移，但报错要能照着做

顶层 `instances:` → `zhaiduo.instances:` 是**破坏性**变更。经确认不做自动迁移，
老配置报错、用户重配。

但 pydantic 默认忽略多余键，直接后果是用户看到一句光秃秃的
`zhaiduo / Field required`，不知道该干什么。加一个 `@model_validator(mode="before")`
把它换成可操作的报错（**这是报错，不是迁移**）：

```python
if isinstance(data, dict) and "instances" in data and "zhaiduo" not in data:
    raise ValueError(
        "配置格式已更新：instances 现在挂在 zhaiduo 模式下。"
        "请删除 config.yaml 后重启，程序会从 config.example.yaml 重新生成一份。")
```

必须放在 `RootConfig` 的 `mode="before"` 里，不能挂在 `load_config()` 上——
`GuiController.load_config` 自己走 `model_validate`，不经过 `load_config()`。

> **发布顺序硬约束**：`config.example.yaml` 必须与代码**同批**更新。
> 否则首启从旧示例生成出来的 `config.yaml` 自己就加载失败，用户连
> "删掉重来"都救不回来。

### 5.3 界面版式

```
central#appRoot（#F0F2F5）
└ appHeader    「RoK 助手」20/600 + 副标题 12 次文
               右：[刷新配置] [⚙ 配置] │ [授权标签] [激活]
└ body QHBoxLayout
   ├ modeNav   左侧导航（宽 160，白底，右侧 1px 分割线）
   │           ● 寨多多模式 / 宝石模式 / 答题模式
   └ modeStack QStackedWidget，每模式一页 ModePage
        ├ 页头：模式名 16/500 ＋ [▶ 开始运行]（主） [■ 停止]（次）
        ├ 1px 分割线
        └ 内容：0=卡片流式网格 / 1=空态 / 2=「该模式尚未开放」占位
└ QStatusBar
```

- 「开始运行 / 停止」从顶部操作栏**下沉**到各模式页头；
  「刷新配置 / ⚙ 配置」是全局动作，**上提**到应用头。
- 三个模式各有一对按钮，但同一时刻只有当前页那对可见——
  「每屏主按钮 ≤ 1」自动成立。
- 未实现的模式：开始按钮**置灰**（保留可见，让用户知道这里将来能跑），
  内容区是占位「宝石模式 · 开发中 / 该模式尚未开放」。
- 窗口 1200×800 → 1280×820（让出 160 的导航宽度后卡片区仍有原宽度）。

### 5.4 互斥运行：一个 `_sync_ui_state()` 收口

现在 `_on_start` / `_on_stop` / `_on_run_finished` / `_rebuild_cards` 里散着
6 处 `setEnabled`。加模式维度后会翻倍，改一处漏一处。改成从**三个输入**
推导全部界面状态：

```
_sync_ui_state()  ← (self._running_mode, page.mode, 有无角色)

  page.start_btn.enabled = 未运行 and page.mode ∈ IMPLEMENTED_MODES
  page.stop_btn.enabled  = 运行中 and 运行的就是这一页
  modeNav.enabled        = 未运行            ← 这就是「运行中锁导航」
  page.body              = 未实现 → 占位；有角色 → 卡片；无角色 → 空态
```

互斥不是靠三处 `if` 维护的，是**从 `_running_mode` 这一个状态推导出来的**。

`GuiController.start(mode: AppMode = AppMode.ZHAIDUO)` 加一道边界检查：模式不在
`IMPLEMENTED_MODES` 就 `error_occurred.emit(...)` 并返回 `False`。这是模式进入
运行时的唯一入口，五行的成本换掉"某个 `setEnabled` 漏了就直接跑起来"。

### 5.5 配置对话框

左树从「全局 / YAML / 各实例」变成：

```
公共配置            基础参数（屏幕 / 路径 / 模型 / 反检测 / 收工阈值）
寨多多模式          ├ 实例 mumu0 → 角色表 + 编辑
                    └ 实例 mumu1 → 角色表 + 编辑
宝石模式            占位「该模式尚未开放，暂无配置项」
答题模式            同上
YAML 原文（高级）    全文件原始编辑
```

「添加实例 / 添加角色」的入口留在寨多多模式下。

  `level_range_low/high.png`，真机跑 11–15 目标时会因缺识别器而抛异常
  （§4.2 表格那一行）。这是本次唯一的外部输入依赖。

  角色配置（模拟器路径由首启自动探测，角色分工/等级/预设要手填）。
- 宝石/答题是**纯占位**，除导航与占位页外没有任何行为。
