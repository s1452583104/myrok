# 宝石模式设计（2026-10-17）

> 状态：**待实现**。本文是设计意图的源头；实现记录写 `docs/HISTORY.md`，
> 当前状态写 `docs/PROGRESS.md`。文档只记字段作用、不记取值——要看配了什么直接读 `config.yaml`。

## 1. 目标

以**模拟器为单位**管理，一个模拟器登录一个角色。登录后检查队列是否已派满；没满就：

长按地图/城堡按钮 → 环形菜单选「资源」→ 进入**资源查看视角**（地图缩小、资源/城堡/野怪
变成小图标）→ 鼠标**回字形螺旋**扫图、同时用 YOLO + 模板找**宝石**资源 → 点宝石放大 →
确认是宝石 → 点开采集框 → 点蓝色「采集」→ 创建部队 → 行军。

重复直到队列派满（`queue_limit`，通常 5–7）。派满后等 20~30 分钟再进下一轮。

### 1.1 不在范围内

- 不采集非宝石资源（木材/粮食/石料/铁矿一律跳过）。
- 不做宝石的「采集完成」确认——派兵发出即算一次采集完成。
- 不做多账号切换（一个模拟器一个角色）。

## 2. 与现有代码的关系

多模式框架（2026-10-13）已经落地：`AppMode.GEM` 已存在、`gem.instances` 是空壳
（`ModeConfig`）、宝石页是 LOCKED 占位、`IMPLEMENTED_MODES` 只含 `ZHAIDUO`。
本设计**只加模式，不改寨子模式的任何行为**。

底座可以直接复用，无需改动：

| 组件 | 位置 | 复用方式 |
|---|---|---|
| `WorkerRunner` | `workers/runner.py` | 原样用。它已经是通用的：吃 `sm_factory` / `handle_source` / `max_rounds`，自带冷却重建、异常退避、`rounds_ok/failed/env` 分结局计数 |
| `preflight()` | `coordination/preflight.py` | 原样用（入参类型放宽，见 §4.3） |
| `TemplateRegistry.build_recognizers()` | `core/template_registry.py` | 原样用 |
| `handle_source.swipe(x1,y1,x2,y2,ms)` | `core/handle_source.py` | **长按 = `swipe(x,y,x,y,800)`**，三个实现（ADB / Win32 / Fake）都支持 |
| `JitteringHandleSource` + `HumanProfile` | `infra/anti_detection.py` | 原样用（反检测与人性化层自动生效） |

**不需要**的东西：事件总线跨实例通信、`ActionLedger`、`RallyEventTracker`、集结前置门槛。
宝石模式每台模拟器**各扫各的**，实例之间没有任何协作——这是它与寨子模式最大的结构差异。

## 4. 配置层

### 4.1 抽 `InstanceBase`

`InstanceConfig` 现在把「模拟器连接方式」和「寨子角色」绑在一起。宝石只需要前者。
把连接字段抽成基类，两边各自继承：

```
InstanceBase        id / name / mumu_index / adb_address / window_title_pattern
                    + 校验：mumu_index 与 adb_address 二选一、角色名不重复
├── InstanceConfig       characters: list[CharacterConfig]      （寨子，原样不动）
└── GemInstanceConfig    characters: list[GemCharacterConfig]   （宝石，恰好 1 个）
```

`GemCharacterConfig` **只有 `id` + `name`**。没有 `role`、没有 `target_levels`、
没有 `march_presets`、没有 `fill_target_leaders`——因为派兵那一步是「表单默认 + 直接点行军」，
不需要任何配置（§6.6）。

### 4.2 `GemConfig`

`GemConfig(ModeConfig)`：模式级参数 + `instances`。

| 字段 | 作用 |
|---|---|
| `queue_limit` | 队列图标数 ≥ 此值 = 派满了，去等 |
| `max_rounds` | 扫图会话轮数上限 |
| `scan_rings` | 回字形向外扩几圈 |
| `scan_drag_px` | 每步拖拽距离 |
| `scan_drag_ms` | 每步拖拽时长 |
| `idle_wait_min` / `idle_wait_max` | 队列满后的等待区间（分钟） |
| `instances` | 本模式的模拟器列表 |

校验只管两件事：`id` 不重复、每台恰好 1 个角色。**不做**「至少一个 leader」这类跨角色
检查——那是寨子的规则（`ZhaiduoConfig._cross_checks` 的注释已经写明「校验跟着数据走，
不跟着模式走」）。

### 4.3 兼容性

`RootConfig.instances_for(mode)` 走 `getattr(self, mode.value).instances`，不用改。
`preflight()` 的入参类型从 `list[InstanceConfig]` 放宽成 `list[InstanceBase]`——
它本来就只读那 5 个连接字段。

## 5. 协调器分层

```
coordination/base_runtime.py    BaseCoordinator：预检 → 装识别器 → 按实例 spawn
                                WorkerRunner → snapshot / stats / stop / _warn_if_alive
coordination/runtime.py         RuntimeCoordinator(BaseCoordinator)  ← 寨子专属：
                                EventBus 路由、ActionLedger、_leaders_done / _stop_members
coordination/gem_runtime.py     GemCoordinator(BaseCoordinator)      ← 只加自己的 stats 口径
```

### 5.1 为什么抽基类而不是复制一份

复制会让「预检 → 装识别器 → spawn」这套启动逻辑变成两份要同步维护的代码。
本仓库的已知问题清单里已经有一类就是「两处描述同一件事的代码互相矛盾」
（PROGRESS 已知问题 16：`queue_verdict` 与两个 `_normalize_view` 对 `map_btn` 的注释互相矛盾）。

### 5.2 为什么不把 `RuntimeCoordinator` 泛化成「接受 mode + SM 工厂」

那等于往里塞事件总线、账本、集结门槛、收工联动这些**寨子专属概念**的条件分支。
宝石模式一个都用不上，改完是给一条已经跑通的实机链路加一堆死代码。

### 5.3 接口不变

`RuntimeCoordinator` 的公开接口（`start` / `stop` / `stats` / `snapshot`）签名不变，
`_run_goal.py` 与 `GuiController` 的调用点一行不改。基类提取是**纯搬运**，不改逻辑。

### 5.4 状态机工厂

`workers/factory.py` 新增 `create_gem_state_machine(char, gem_cfg)`，与现有
`create_state_machine` 并列。

## 6. 状态机（`workers/gem_sm.py`）

```
IDLE → NORMALIZE → COUNT_QUEUES
COUNT_QUEUES:
    队列数 >= queue_limit → WAIT → 回 COUNT_QUEUES（本轮内最多等一次，再满就本轮结束）
    队列数 <  queue_limit → OPEN_RESOURCE_VIEW
OPEN_RESOURCE_VIEW:  长按 map_btn(95,990) → 等环形菜单 → 点资源按钮 → 确认进了资源视角
SCAN:                螺旋一步 → swipe → 截帧 → 找 gem_icon
                     每圈结束数一次队列，满了就提前收本轮
                     找到 → ZOOM_CONFIRM ｜ 走完 scan_rings 圈 → ROUND_DONE
ZOOM_CONFIRM:        点图标 → 认 gem_mine_zoom
                     是 → COLLECT_DIALOG ｜ 否 → 关掉 → 回 SCAN（该点记入「已试过」）
COLLECT_DIALOG:      等采集框 → OCR 判「宝石矿床」
                     是 → CLICK_COLLECT ｜ 否 → 关掉 → 回 SCAN
CLICK_COLLECT → CREATE_TROOP → FILL_FORM（只点行军）
                     发车验证通过 → 回 COUNT_QUEUES（重新数，决定继续还是等）
ROUND_DONE → END     （runner 冷却 30s → 重建 SM → 下一轮）
```

### 6.1 一轮的定义

**一轮 = SM 从 `IDLE` 起步到 `ROUND_DONE` 的整条链**。链内可能包含**多次**
「进资源视角 → 螺旋 → 派兵」（每派完一队就回 `COUNT_QUEUES` 重新数）。

链只有两个出口，都走 `ROUND_DONE`：

- **(a) 扫空**：某次 `SCAN` 走完 `scan_rings` 圈、一圈都没找到宝石；
- **(b) 等满**：`COUNT_QUEUES` 遇到队列已满，`WAIT` 之后还是满。

注意 (b) 会在「派完最后一队、队列刚好满」时命中——所以一轮的实际结束点通常是
「队列被这一轮派满了」。轮数由 `WorkerRunner` 现成的 `rounds_ok/failed/env`
统计接住，统计条口径与寨子模式一致。

**每派完一队就回 `COUNT_QUEUES` 重新数**，而不是「继续扫」：因为队列可能在派兵的
过程中刚好满，继续扫就是白扫。

### 6.2 队列计数的主判据是「数图标」

`COUNT_QUEUES` **数 `queue_*_icon` 命中的个数**（`queue_gather_icon` / `queue_march_icon`
/ `queue_flag_icon` / `queue_return_icon` 等），与 `queue_limit` 比较。这是配置写死的
那条判据。

`queue_badge`（「N/M」计数角标）**只作为交叉验证写进日志**，不参与裁决——
主判据只留一条，避免「两个数不一致时听谁的」这种没有答案的分支。
日志里两者不一致时打 warning，供实机定标时参考。

### 6.3 `WAIT` 用 deadline，不阻塞

进入 `WAIT` 时记 `deadline = now + U(idle_wait_min, idle_wait_max)`；每次 `step()`
只查一下到点没、立刻返回。runner 每步之间有 2s 轮询，25 分钟 ≈ 750 次空转。

- 好处：**Stop 的响应延迟仍是 2s 级别**，不用给 `StateMachine` 基类加可中断 sleep
  （改基类会波及寨子那两条已跑通的链路）。
- 不刷日志：`WorkerRunner._set_status` 对相同状态去重。

### 6.4 本轮内最多等一次

`COUNT_QUEUES` 满 → `WAIT` → 再数；**还满就本轮结束**。这样 `max_rounds` 对总时长
有界（10 轮 ≈ 最多 10 次等待），不用额外加「单轮最多等几次」的配置项。
用户若发现 25 分钟不够部队返城，调 `idle_wait_min/max` 即可。

### 6.5 螺旋路径

从当前相机位置出发，右 1 → 下 1 → 左 2 → 上 2 → 右 3 → 下 3 → … 经典向外螺旋，
单位步长 `scan_drag_px`。路径生成是纯函数，单独测。

每次 `FILL_FORM` 成功（派完一队）后回 `COUNT_QUEUES`；若队列仍未满则重新
`OPEN_RESOURCE_VIEW` → `SCAN`。**螺旋从当前位置重新起步**（相机在点宝石时已被拉走，
所以实际是从上一个宝石附近继续向外），并用「本次进入资源视角后已试过的坐标」集合
避免对同一个图标反复点。

### 6.6 `FILL_FORM` 只点行军

表单打开时武将已默认选中、兵力已有默认值，**不点「最大」、不选兵种**，
直接点 `march_btn`(1416,934)。

加一条兜底：**行军点击后要验证发车了**（队列数 +1，或画面回到地图）。
因为「默认」是游戏记住的上次设置，万一是 0 兵，行军会点不动——这种情况按
**干净中止本轮**（`fail_reason=march_rejected`）处理，**不抛异常**。抛异常会被 runner
当成可退避重放的步骤失败、不重建 SM、同状态重放 6 次就停机——这个坑仓库里已经踩过两次
（PROGRESS 已知问题 8 与 14）。

## 7. 错误路径

全部写 `fail_reason` + 走 END 边，**绝不抛异常**。

| `fail_reason` | 触发 | 计入连续失败？ |
|---|---|---|
| `normalize_stuck` | 归一化认不出地图视图 | 否（环境类） |
| `queue_unknown` | 队列栏认不出来 | 否 |
| `radial_menu_missing` | 长按后环形菜单没弹 | 否 |
| `resource_view_failed` | 点了资源按钮没进资源视角 | 否 |
| `gem_confirm_failed` | 连续 `_GEM_CONFIRM_MAX`（3）个宝石点都确认不了 | 否 |
| `march_rejected` | 行军点了没发车（默认兵力可能是 0） | **是** |
| `collect_rejected` | 点采集后创建部队气泡不弹 | **是** |
| `form_missing` | 创建部队表单不弹 | **是** |

后三条计入连续失败，是为了让 `max_consecutive_failures` 真的能兜住「账号没兵 /
队列其实满了 / 表单改版」这类**持续性**故障。如果全判环境类，程序会永远转下去。

### 7.1 扫空算正常结束

走完 `scan_rings` 圈没找到宝石 = **本轮正常结束**（`fail_reason=None` → `rounds_ok`）。

代价：「识别器坏了」和「附近真没宝石」在统计上分不开。**不为它加停机逻辑**，
只打一条每轮检出数的日志。这与仓库已有的「成员连续空波只打 warning、不自行停」
是同一个裁定（PROGRESS「本分支未决项」最后一条），保持一致。

#### 8.2.1 定案：「进没进资源视角」用**相对边缘密度**判，不做成模板

「已经进了资源视角」这一步**不做成 manifest 模板**，改由 `workers/gem_sm.py` 用**相对**边缘
密度判：

> 进资源视角前先量一次地图主体的边缘密度 `before`，点完资源按钮后再量 `after`；
> `after >= before * 1.5` 才算进去了。

**为什么不做成模板**（`resource_view_anchor` 被否）：资源视角里到处是小图标，任何一张静态
模板都会被别的图标误命中；而做成**绝对**像素阈值又活不过不同账号的地图内容差异。相对判据
的好处是**不需要新模板、不需要标定绝对阈值**。

**代价**：「进视角失败」和「地图本来就很密」在数值上可能混同。所以判据失败时记
`resource_view_failed` **干净中止本轮**（设 `ctx["fail_reason"]` + 走 `END` 边），
**不重试**——重试只会在同一帧上得出同一结论。

实现见阶段 3 的 `OPEN_RESOURCE_VIEW`（`_open_resource_view` → 出口 guard
`fail_reason in (radial_menu_missing, resource_view_failed)` 走 `END`，否则进 `SCAN`）。

（原「候选 B：环形菜单的『资源』按钮变黄」已随定案作废：待验项 2 的「黄色 = 当前选中视角
还是手指悬停」始终未验，且相对边缘密度不依赖它。）

## 12. 已知局限（v1 接受）

1. **识别器失效与「附近没宝石」在统计上分不开**（§7.1）。靠日志里的每轮检出数人工发现。
2. **队列计数复用寨子的 ROI**，而世界地图右上角有小地图、城内没有。待验项 1 若证明
   两者冲突，`COUNT_QUEUES` 的 ROI 需要单独定标（状态机不用改，只是 `_count_queues()`
   这一个函数换 ROI）。
3. **「已试过的坐标」只在单次进入资源视角内有效**，不跨会话——重进资源视角后
   同一片区域会被重扫。靠采集框里的「采集者」字段兜住重复采集（被自己采过的点
   会显示自己的名字）。
4. **不处理「队列其实满了但图标没认出来」**：这种情况下会走到 `collect_rejected`
   （点采集后气泡不弹），计入连续失败，靠 `max_consecutive_failures` 兜。
5. **不处理体力**：宝石采集消耗行动力，v1 不做补充（寨子模式那套 `ap_refill`
   是否复用留待实机观察后再定）。
6. **待验项全部未验**：§3.2 五条目前只有静态帧推断，没有真机证据。
