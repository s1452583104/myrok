# 授权与发码平台 —— 设计

> 日期：2026-10-08　状态：待实现
> 前置：`docs/superpowers/specs/2026-07-15-rok-assistant-design.md`（程序本体）
> 相关：`docs/PACKAGING.md`（绿色 zip 发行）、`docs/PROGRESS.md` 已知问题 10（冻结包 WMI 慢）

## 1. 目标

给已经分发出去的绿色 zip 加一层授权：

1. **默认试用一个月**，无需任何操作即可用。
2. **试用到期后需要激活**才能继续跑任务。
3. **防伪激活**：用户**重新解压一份新包不能刷新试用期**。
4. **发码平台**：作者自己用的小工具，能签发「延长 N 天」和「永久授权」两种码。

## 2. 已定决策（来自 2026-10-08 brainstorm）

| 决策点 | 选择 | 影响 |
|---|---|---|
| 激活方式 | **纯离线码** | 不需要服务器 / 域名 / 运维；用户机器不联网；每单需人工过一次手 |
| 防重置强度 | **防有点技术的** | 指纹严格绑定 + 多源交叉校验 + 异常静默降级；接受偶尔误伤 |
| 换机售后 | **放宽到不误伤重装** | 指纹主项取硬件级（主板/CPU）；系统盘、MAC、机器名变化不影响 |
| 发码工具 | **PyQt6 小工具** | 复用现有 venv 与界面风格；不进发行包 |
| 到期表现 | **能进界面，不能跑任务** | Start 保持可点，点击即弹激活窗、任务被拒；用户看得到自己的配置还在 |
| 试用期存储 | **三处冗余 + 取最早** | 重新解压只清掉其中一处 |
| 签名实现 | **`cryptography`** | 发行包 +约 10MB（现 326MB，+3%） |

## 3. 架构总览

### 3.1 新增模块（客户端）

`src/rok_assistant/infra/licensing/`，与现有 `infra/` 平级，**纯离线、不碰网络**：

| 模块 | 单一职责 | 依赖 |
|---|---|---|
| `fingerprint.py` | 采硬件标识 → 主指纹 / 次指纹 → 机器码 | `winreg` + WMI |
| `store.py` | 三处冗余读写 + HMAC 校验 + 取最早 + 自愈补写 | `winreg` + 文件系统 |
| `codec.py` | 激活码编码 / 解码（base32 + 分组 + 输入清洗） | 标准库 |
| `verify.py` | 用内嵌公钥验签 | `cryptography` |
| `pubkey.py` | 内嵌公钥（**生成物，入库**） | — |
| `state.py` | 汇总：试用起点 / 到期日 / 永久 / 已用 serial | 上面四个 |
| `guard.py` | 唯一门面：`current_guard()` / `status()` / `activate()` / `machine_code()` | `state` |

**`guard` 是唯一接缝。** GUI 与 worker 只认 `guard`，不认识下面任何一个模块——这样测试可以整体替换它，实现改动也不会渗到界面代码里。

### 3.2 数据流

```
启动 ─→ guard.status()
          ├─ fingerprint.main_fingerprint()   （WMI，约 1~2s）
          ├─ store.read()                     （三处 → 验 HMAC → 取最早）
          ├─ state.effective_expiry()         （试用 / 激活 / 永久）
          └─ LicenseStatus(kind, expiry, days_left, machine_code)
                    ↓
             状态栏标签 + Start 是否可用

激活 ─→ guard.activate(code)
          ├─ codec.decode()   → 失败「激活码格式不正确」
          ├─ verify.check()   → 失败「激活码无效」
          ├─ fp 比对本机       → 失败「激活码与本机不匹配」
          ├─ serial 未用过     → 失败「该激活码已被使用」
          └─ store.write()    → 三处一起写
```

## 4. 机器指纹

### 4.1 主项 / 次项

| 类别 | 来源 | 是否参与判定 |
|---|---|---|
| **主项** | 主板 UUID（`Win32_ComputerSystemProduct.UUID`） | **必须全匹配** |
| **主项** | CPU ID（`Win32_Processor.ProcessorId`） | **必须全匹配** |
| 次项 | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | 只记录 |
| 次项 | 系统盘卷序列号 | 只记录 |
| 次项 | MAC 地址 | 只记录 |
| 次项 | 机器名 | 只记录 |

`MachineGuid` **特意放次项**：它随 Windows 安装生成，重装系统就会变；当主项会误伤「重装系统」这个最常见场景，而用户明确选了「不误伤重装」。

主项全是硬件级，所以**重装系统、换硬盘、插拔网卡都不影响指纹**；只有换主板 / 换 CPU 才需要重新发码。

### 4.2 机器码

```
fp_main  = SHA256( normalize(mainboard_uuid) + "|" + normalize(cpu_id) )    # 32 字节
machine_code = base32(fp_main[:10]) + check_char                            # 17 字符
```

`10 字节 = 80 位 = 16 个 base32 字符`（刚好整除，无填充）。第 17 位是校验字符：

```
check_char = BASE32[ SHA256(b"rok-mc-check" + fp_main[:10])[0] >> 3 ]
```

校验字符**只吃前 10 字节**（也就是机器码里显示的那 16 个字符），不是整个
`fp_main`：发码工具只拿得到这 17 个字符，如果校验字符依赖它看不到的另外
22 字节，§9 的「机器码校验字符不过就当场报错」就根本实现不了。

显示成 `XXXX-XXXX-XXXX-XXXX-C`。**校验字符是给人工环节兜底的**——机器码靠用户手抄或截图转述给你，抄错一位是最常见的故障；有校验字符你能当场发现，不必来回三轮。

`normalize()`：转大写、去空白与连字符、去 `0x` 前缀、补零对齐。

### 4.3 WMI 降级路径

WMI 查询在**冻结包里慢**（`docs/PROGRESS.md` 已知问题 10：MuMuManager 慢 4~6 倍）。所以一次启动**只查一次**，走启动 splash 遮住这 1~2s。

### 4.4 指纹解析顺序（**这一条是防「WMI 偶发失败白送试用期」的**）

如果 WMI 偶发失败就直接改用 `MachineGuid` 当主指纹，会踩一个**致命坑**：指纹一变 → 三处记录的 HMAC 全验不过 → 被当成「首次运行」→ 把新的 `trial_start` **覆盖写进三处**，用户的试用期就此重置，而且是永久性的（原记录被覆盖了）。

所以解析顺序是：

1. **先读缓存**：从三处记录里取 `fp` 字段（指纹本身不是秘密，记录里的 `fp` 就是缓存）
2. **再算 WMI**
   - WMI 成功 → 用算出来的（**主板真的换了也走这条**）
   - WMI 失败但**有缓存** → **用缓存**（判定为 WMI 偶发故障，不是换机器），记日志
   - WMI 失败且**无缓存** → 才降级用 `MachineGuid`，记日志 `指纹降级：WMI 不可用且无缓存`

缓存只在 WMI **失败**时兜底，所以它不构成绕过：攻击者改缓存里的 `fp` 只会让自己的激活码绑不上。

**降级路径（用 `MachineGuid`）下重装系统会换指纹 → 需要重新发码**，属已知局限 5。

## 5. 试用期存储与防重置

### 5.1 三处冗余

| # | 位置 | 说明 |
|---|---|---|
| 1 | 注册表 `HKCU\Software\RoKAssistant\License`，值名 `state` | 重新解压**清不掉** |
| 2 | `C:\ProgramData\RoKAssistant\license.dat`（隐藏 + 系统属性） | 重新解压**清不掉** |
| 3 | `<user_dir>\.roklicense`（隐藏属性） | 重新解压会清掉 |

**重新解压只会清掉第 3 处，1 和 2 留着——这就是防「解压刷新试用期」的全部机制。**

写入失败（如 `ProgramData` 无权限）**静默跳过**、只记日志；剩两处照常工作。

### 5.2 记录格式

每处存同一份记录（注册表里是 base64）：

```json
{
  "v": 1,
  "fp": "<主指纹摘要 hex，64 字符 = 完整 32 字节>",
  "trial_start": 1759996800,
  "last_seen":   1760083200,
  "licenses":    [{"code": "<122 字符激活码>", "applied_at": 1760000000}],
  "hmac":        "<hex，32 字符>"
}
```

```
key  = SHA256(fp_main_bytes + b"rok-lic-v1")
hmac = HMAC_SHA256(key, json_without_hmac_sorted_keys)[:16].hex()
```

`fp` 存**完整 32 字节**（不是摘要的摘要）：§4.4 的指纹缓存要拿它当整份 `fp_main` 用，只存 8 字节的话缓存就废了。

**HMAC 密钥由主指纹派生**，所以记录**拷到别的机器上验不过**——用户没法把一份「全新试用期」的记录拷过来覆盖本机的。

### 5.2.1 为什么存「激活码列表」而不是「到期日」

到期日**不落盘**，每次启动从 `licenses` 里的码现算。原因是叠加语义：试用还剩 20 天时输入「延长 30 天」的码，到期日 = 试用到期日 + 30 天；用户再输入第二个 30 天码时还要在这之上继续加。**单个到期日标量表达不了这个结果**，必须保留每个码及其累加基准。

每条码带一个 `applied_at`（激活当时的 `effective_now`），用于「已过期时从今天起算 N 天」这条规则。计算时 `applied_at` 被 `last_seen` 夹住：

```
applied_at = min(applied_at, last_seen)
```

这个夹取是自洽的：把 `applied_at` 改大会被夹回 `last_seen`，而把 `last_seen` 改大会让 `effective_now`（§5.4）一起跳到未来，**反而让所有授权当场过期**——改哪个都占不到便宜。

**这样设计的收益**：伪造到期日需要**私钥**，而不只是 HMAC 密钥。HMAC 密钥 = `SHA256(主指纹 + 固定 salt)`，主指纹的输入全在用户自己的机器上，**理论上用户算得出来**；私钥则永远只在发码端。所以「到期日由签名的码现算」比「到期日落盘 + HMAC」严格更强，代价只是记录里多一个列表。

### 5.3 读取规则

1. 三处逐一解析 → 验 HMAC → 验 `fp` 等于本机主指纹摘要；通过者为「有效」
2. 有效记录里：
   - `trial_start` 取**最早**（保守：剩余试用期最少）
   - `last_seen` 取最大
   - `licenses` 按 `code` 里的 `serial` 去重取**并集**；同一 serial 出现多次时取 `applied_at` **较小**的那条（与「取最早」同向的保守选择）
3. **自愈**：把合并后的记录补写回所有三处（修好被删/损坏的那几处）

### 5.3.1 「没有记录」和「有记录但全是假的」必须分开处理

这两者看起来都是「有效记录为空」，但**绝不能混为一谈**——混了就等于给了一条重置路径：

| 情形 | 判定 |
|---|---|
| 三处**都不存在** | 首次运行，`trial_start = now` |
| 三处**存在但 HMAC / `fp` 验不过** | **判为篡改** → 授权状态强制 `expired`（静默）。**绝不重置试用期** |
| 记录存在但**版本号不认识**（`v` 不是 1） | 视为「不存在」，**不算篡改** |
| 记录存在但**结构损坏**（JSON 解析失败 / 缺字段） | 视为「不存在」，**不算篡改** |

第 3、4 行是给未来的自己留的活路：将来记录格式升级到 `v: 2` 时，旧版本记录不能被判成篡改，否则**用户升级程序就会当场被锁死**。只有「版本认得出、结构完整、但 HMAC 对不上」才是篡改。

但要看清第 4 行的边界：**结构损坏**（JSON 坏 / 缺字段）本身也是一条重置路径——把**三处都改坏**结构（例如删掉 `hmac` 字段）会被当成首次运行，试用期照重置。这与「三处都删干净」（§12 第 2 条）同档同效，是「为将来升级留活路」的代价，不是新漏洞；记在 §12 第 7 条。

第 2 行的代价：用户把**用过的整个文件夹**拷到另一台机器（新机器上注册表与 `ProgramData` 为空，只有文件夹里那份记录）→ 会被判篡改，拿不到新机器的试用。这个场景很少见——正常分发走的是 zip，zip 里不含记录——但它确实存在，记在已知局限里。

反过来说，**重装系统不会触发这一条**：主项是主板 + CPU，重装不换硬件，记录里的 `fp` 仍然匹配，所以「程序装在 D 盘、重装 C 盘」的用户试用期照常保留——这正是「不误伤重装」想要的。

### 5.4 时钟回拨

两条规则同时生效：

```
effective_now = max(系统时间, last_seen)        # 调回时间不给任何好处
last_seen     = effective_now                   # 只增不减
```

- 系统时间被调回（哪怕只调 1 小时）→ `effective_now` 仍是 `last_seen`，试用期**不倒退**
- 回拨超过 **24h 容差** → 额外判定为**篡改** → 授权状态强制 `expired`，**静默**（界面只说「试用已结束，请输入激活码」，真实原因只进日志）
- 交叉校验：任一存储文件的 mtime 晚于当前时间 24h 以上 → 同样判定为篡改

24h 容差是为了不误伤时区 / 夏令时 / NTP 微调 / 用户手动校时。

### 5.5 试用期天数写死在代码里

`state.TRIAL_DAYS = 30` 是**代码常量，不进 `config.yaml`**。

`config.yaml` 是用户能直接编辑的文本文件——把试用期天数放进去等于送一个一键改试用期的开关。同理，**公钥也写在 `pubkey.py` 里，不进配置**。

## 6. 激活码格式与验签

### 6.1 布局

```
code_bytes = payload(12) + signature(64) = 76 字节
code       = base32_nopad(code_bytes)     = 122 字符
显示        = 5 个一组，共 25 组
```

**122 个字符是完整的 Ed25519 签名（64 字节）逼出来的**，不是设计失误——理由见 §6.2。激活码靠微信/QQ 复制粘贴传递，122 字符对粘贴没有影响；对话框里按等宽字体折行显示。

`payload`：

| 字段 | 字节 | 说明 |
|---|---|---|
| `ver` | 1 | 格式版本，当前 `0x01` |
| `fp_main` | 6 | 主指纹摘要前 6 字节——**码绑机器** |
| `kind` | 1 | `0x01` 延长 N 天 / `0x02` 永久 |
| `days` | 2 | 延长天数（永久时 0），上限 65535 天 |
| `serial` | 2 | 发码流水号，用于**防重放** |

### 6.2 为什么签名不能截断（**这一条是纠正，别按「截断」去实现**）

最初的设想是「签名截断到 16 字节，把码压到 45 字符，128 位仍然够安全」。**这个想法是错的，而且错得会让程序根本跑不起来。**

Ed25519 验签要算 `[S]B == R + [k]A`（`k = SHA512(R ‖ A ‖ M) mod L`）——**R 和 S 两个分量都必须完整**。把 64 字节砍成 16 字节，验证方连方程都列不出来，这不是「安全性略降」，是**无法验证**。ECDSA 同理（r、s 都不能截断）。

能压到 45 字符的只有 **HMAC（对称密钥）**，但那要求把密钥内嵌进客户端。**代价是全局性的**：任何人从 exe 里挖出这个密钥，就能给**所有人**签发永久码，一条帖子废掉整套授权。相比之下，非对称方案被破只是「那个人 patch 自己那份 exe」。

所以选完整签名。76 字节是 128 位安全级别下**最短的公开可验证**方案：

| 方案 | 签名长度 | 结论 |
|---|---|---|
| Ed25519 | 64 字节 | **选它**：最短的 128 位安全公钥签名，`cryptography` 直接支持 |
| RSA-1024 | 128 字节 | 更长 |
| ECDSA P-192 | 48 字节 | 短 26 字符，但 96 位安全且已被弃用，不值得 |
| HMAC-SHA256 | 16 字节 | 最短，但密钥内嵌 = 全局失守 |

验签用 `cryptography` 的 `Ed25519PublicKey.verify()`。

### 6.3 输入清洗

用户粘贴时自动：转大写、去空白与连字符、映射 base32 字母表外的易混字符（`0→O`、`1→I`、`8→B`、`9→G`）。这四个字符**不在** RFC4648 base32 字母表（`A-Z2-7`）里，所以映射是无损的。

### 6.4 四步校验与提示粒度

| 步骤 | 失败时提示 |
|---|---|
| 解码 / 长度 | 「激活码格式不正确」 |
| 验签 | 「激活码无效」 |
| `fp_main` 比对本机 | 「激活码与本机不匹配」 |
| `serial` 未用过 | 「该激活码已被使用」 |

**「静默」只适用于防重置被触发时**（时钟回拨 / 存储异常）——那种情况界面一律显示「试用已结束，请输入激活码」。

**激活失败必须给粗粒度原因**，否则用户无法自助。区分「无效」和「与本机不匹配」不泄露任何东西：用户拿到别人的真码也照样用不了。

## 7. 授权状态机

### 7.1 落盘的只有三个量

`trial_start`、`last_seen`、`licenses`（激活码列表）。

到期日与 `permanent` **不落盘**，每次启动从 `licenses` 现算（§5.2.1）——伪造它需要私钥。`used_serials` 也不单独存，从 `licenses` 里每条码的 `serial` 直接读出来。

### 7.2 到期日（纯函数，从签名数据现算）

```
expiry = trial_start + TRIAL_DAYS(30) 天
for 每条码（按 serial 升序，保证结果与顺序无关）:
    if 验签失败            → 丢弃该条
    if kind == 永久        → 直接返回「永不过期」
    base   = max(expiry, min(applied_at, last_seen))
    expiry = base + days 天
```

按 serial 升序排序是必须的——否则「先加 30 再加 7」和「先加 7 再加 30」在已过期的边界上结果不同，而记录合并（§5.3）后列表顺序可能变。

### 7.3 激活时的叠加语义

```
延长 N 天：new_expiry = max(当前到期日, 今天) + N 天
永久     ：permanent = True
```

- 试用还剩 20 天时输入「延长 30 天」→ **共 50 天**（不是从今天算 30 天）
- 已过期时输入 → 从今天起算 N 天
- 已永久时再输码 → **幂等接受，不报错**（用户可能重复购买，报错会引发售后）

`serial` 靠「`licenses` 里已有该 serial 就拒绝」实现防重放，**同一个码不能吃两次**——这是防「一个延长码反复输入无限续期」的唯一手段。`licenses` 全清掉后旧码可再用一次，属已知局限 2。

### 7.4 对外状态

对 GUI 只暴露四种，`tampered` 在内部降级成 `expired`：

```python
LicenseStatus(kind, expiry: date | None, days_left: int | None, machine_code: str)
# kind ∈ {"trial", "licensed", "permanent", "expired"}
```

## 8. 客户端集成

### 8.1 四个接入点

| 位置 | 改动 |
|---|---|

### 8.2 测试隔离（**必做，否则测试会污染开发机**）

`tests/` 里 `test_gui_smoke.py` 每条用例都新建 `MainWindow`。如果它直接读真实注册表 / `C:\ProgramData`，**跑一次测试就会往开发机的注册表里写试用记录**，而且每条用例写一次。

- **不提供环境变量旁路**。`ROK_LICENSE_OFF=1` 这种开关用户一样能设，等于送一个一键破解。宁可不留。
- 改为**依赖注入**：`guard.py` 提供 `current_guard()` 与 `_set_guard_for_tests(g)`；`tests/conftest.py` 加 **autouse fixture**，注入一个「存储根指向 `tmp_path` + 指纹固定为测试值」的 guard。
- 这样所有测试（含已有的 GUI 冒烟）自动隔离，不需要逐条改；同时避免每条用例都跑一次 1~2s 的 WMI。

### 8.3 `--selftest`

加**两项**：

1. 打印授权状态 + **机器码**（用户报障时直接抄这一行给你）。**不做拦截**——它是诊断工具，被授权挡住反而查不了问题。
2. 「授权链自检」：`cryptography` 能否导入、内嵌公钥能否加载、用测试向量验一次签名往返。这一项是给**冻结包**兜底的——`cryptography` 有 C 扩展，是本次唯一新增的二进制依赖，绿色包最容易在这里缺东西，而缺了的表现是「所有激活码都无效」，极难远程排查。

## 9. 发码工具 `tools/license_tool.py`

PyQt6 小工具，**不进发行包**。

- **首启**：`secrets/license_private.key` 不存在 → 生成 Ed25519 密钥对，并把公钥写进 `src/rok_assistant/infra/licensing/pubkey.py`（提示你提交它）
- **主界面**：粘贴机器码 → 选「延长 N 天 / 永久」→ 出激活码（一键复制）
- **校验输入**：机器码的校验字符不过就当场报错，避免发出一个永远激活不了的码
- **台账**：`secrets/issued.csv` 追加记录（时间 / 机器码 / 类型 / 天数 / serial / 激活码），可列表查看
- serial 自动取台账最大值 +1，**跳过已用过的**

## 10. 密钥管理与打包

- `secrets/license_private.key` → **必须进 `.gitignore`**。丢了就没法再发新码（**已发的码仍然有效**，因为公钥没变）——工具首启会提示你备份
- `pyproject.toml` dependencies 加 `cryptography>=42`
- `tools/build_package.py` 的产物断言**加一条**：包里出现 `license_private.key` 或 `secrets/` 一律构建失败。这条是防止手滑把私钥打进发行包的保险丝，比任何文档提醒都可靠

## 11. 测试策略

`tests/unit/infra/licensing/` 按模块分组，固定测试密钥对放 `tests/fixtures/licensing/`。

| 用例组 | 要覆盖的 |
|---|---|
| `fingerprint` | 规范化确定性、机器码长度与校验字符、**WMI 失败但有缓存 → 用缓存**、WMI 失败且无缓存 → 降级 MachineGuid |
| `store` | 三处冗余**取最早**、`licenses` 按 serial **并集去重**、部分损坏**自愈补写**、HMAC 跨机器**验不过**、写失败静默跳过 |
| `store` 判定边界 | 三处**全无** → 首次运行；三处**全无效** → 判篡改**不重置**；**版本号不认识** → 视为不存在；**结构损坏** → 视为不存在 |
| `clock` | 回拨不给好处（`effective_now`）、超 24h 判篡改、容差内不触发、mtime 交叉校验 |
| `codec` | 编解码往返（76 字节 ↔ 122 字符）、分组、输入清洗（含 `0/1/8/9` 映射）、长度不对时拒绝 |
| `verify` | 有效码通过、payload 被改后验签失败、别的机器的码失败、已用 serial 拒绝、**用真公钥验真签名** |
| `state` | 30 天边界、叠加语义（剩 20 + 30 = 50）、**多个码按 serial 排序后累加与输入顺序无关**、已过期从今天起算、`applied_at` 被 `last_seen` 夹住、永久幂等、serial 重放拒绝 |
| `guard` | 四种对外状态、`tampered` 降级成 `expired` |

其中 **`store` 判定边界**那一组是本设计的要害：它直接对应 §5.3.1——「有记录但全是假的」如果被误判成「没有记录」，用户删掉 HMAC 就能重置试用期，整套机制当场失效。这一组测试必须先写。

按 TDD 走：先写失败测试再实现。

## 12. 已知局限

**这一节原样保留，不粉饰。** 离线授权有硬上限，用户应当知情。

1. **已经发出去的旧包不受约束。** 那些包没有授权机制，老用户可以一直用。授权只对新包生效——离线方案 + 已分发的事实决定的，**无解**。
2. **三处存储全部删干净 = 可重置试用**，且 `used_serials` 一并丢失，旧延长码还能再吃一次。这是「三处冗余」这一档的固有上限；要堵死需要联网校验，而本项目选了离线。注意这与 §5.3.1 不冲突：**删掉**是「没有记录」（新试用），**改坏**是「有记录但无效」（判篡改锁死）。
3. **改代码跳过校验可行**（PyInstaller 的 pyc 能反编译）。已明确选择不做反逆向加固。同理，**记录里的 HMAC 密钥是可以推出来的**（主指纹的输入全在用户机器上），所以 HMAC 挡的是「随手改 JSON」，不是有备而来的伪造——真正扛伪造的是**激活码的签名**（§5.2.1）。
4. **时钟回拨的误伤面**：主板电池没电 / 系统时间被重置到过去的用户会被判篡改、试用立即结束。他们仍可正常购买激活（激活后的到期日是绝对日期）。这是「防有点技术的」这一档明确接受的代价。
5. **WMI 降级路径下**（用 `MachineGuid` 当主指纹）重装系统会换指纹，需要重新发码。正常路径不受影响（§4.4）。
6. **把「用过的整个文件夹」拷到新机器**会被判篡改（§5.3.1），拿不到新机器的试用。正常分发走 zip、zip 里不含记录，所以这个场景只有用户自己整目录搬家才会遇到。
7. **把三处记录都改坏结构**（JSON 解析失败 / 缺字段，例如删掉 `hmac`）会被当成首次运行，**同样重置试用期**——与第 2 条「全删干净」同档同效。这是 §5.3.1 第 4 行「结构损坏视为不存在」（为将来格式升级留活路）的代价，不是新漏洞。注意与第 2 条的措辞区别：改坏**内容**但结构完整才是「有记录但无效」（判篡改锁死），改坏**结构**会退回「没有记录」。

## 13. 明确不做（YAGNI）

- 在线激活 / 联网校验 / 远程吊销
- 防逆向加固（加壳、代码混淆、字符串加密）
- 试用期功能阉割（限轮数、限账号数）
- 一码多机、并发机器数限制
- 发码平台的用户体系 / 权限 / Web 化
