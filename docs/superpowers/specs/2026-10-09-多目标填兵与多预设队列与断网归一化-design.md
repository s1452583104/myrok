# 多目标填兵 · 多预设队列 · 断网弹框归一化 —— 设计

> 2026-10-09。三个改动合并成一个 spec，因为它们都动「一轮」的边界与状态机出口，
> 分开做会互相踩。P3 依赖用户 2026-10-09 提供的实机截图。

## 0. 背景与目标

| # | 现象 | 目标 |
|---|---|---|
| P1 | 三个模拟器 A/B/C，C 给 A、B 填兵；A、B 同时发起集结后 **C 只给第一个（A）填了兵** | C 收到一次信号就把**本轮点名的车头全部填掉** |
| P2 | 车头一轮只能用一个预设，前一个没回来就得干等，效率低 | 车头可配**有序多预设**，第一个选不中就换第二个；「返回中」不再阻塞整轮 |
| P3 | 网络不稳弹**蓝色异常框**，盖住界面元素导致识别失败 | 遇到它先点「确定」回主页面，再归一化 |

## 1. 决策记录（用户 2026-10-09 拍板，勿重问）

1. **P1 填兵不记轮次**：成员「只要收到填兵信号就去填」，没有体力就补体力；
   车头跑完 → 协调器停成员。
2. **P1 一轮内连续填完所有目标**（不是一轮一填）。
3. **P1 找下一个目标的等待窗口 = 5s**。
4. **P1 体力「吃到没道具为止」**。
5. **P2 「返回中(黄色箭头)」放行**，但必须**强制换用可用预设**（推翻 2026-09-16
   「返程态阻塞」的结论——那次事故的成因是「点了预设但没确认、游戏用默认武将代开车」，
   本设计用**确认失败即换下一个预设、全失败即抛异常**堵住它，而不是靠阻塞整轮）。
6. **P2 配置形态**：有序列表，每项自带兵种。**预设号取值域保持 1..5**。
7. **P2 GUI**：3 行固定编辑器（每行 `[预设 ▾][□步兵 □骑兵 □弓兵]`，
   第 2/3 行可留空，行序即优先级）。
   > 实现修正（2026-10-09）：原措辞是 `[预设 ▾][兵种 ▾]`（单选）。但一个预设
   > 允许同时点多个兵种（`_form_troop` 逐个点 `troop_*`），单选下拉是功能倒退，
   > 故兵种用复选框。
8. **P3**：点「确定」按钮后归一化。

## 2. P1 —— 成员填兵改为波次驱动

### 2.1 现状与根因

`member_sm._poll_join`（`src/rok_assistant/workers/member_sm.py:245`）遍历
`fill_targets`，**命中第一个就 return**；填完走 `JOIN_CHECKED → END`，
`is_terminal()`（同文件 `:330`）为真 → runner 计一轮、冷却 30s、重建 SM；
新 SM 只等**新**事件，而 `runtime._make_router`（`coordination/runtime.py:212`）
只在 SM 处于 `IDLE/WAIT_LAUNCH_EVENT` 时投递事件，且 `on_rally_launched` 是
**单槽覆盖**（`member_sm.py:129`）。→ A、B 同时发起时，B 的事件必被丢弃。

### 2.2 目标行为

一次 `rally_launched` 信号 = 一个**波次**：把 `fill_targets` 里**尚未填过**、
且当前战争列表里刷得出来的车头**依次填完**，然后回到等待下一个信号。

### 2.3 状态机改造

`ctx` 新增：

- `filled: set[str]` —— 本波已填过的车头名（去重，防止重复填 A）。
- `next_deadline: float | None` —— **「找下一个目标」的搜索窗口**。
  `_poll_join` 第一次真正去搜下一个目标时设
  `time.time() + _WAVE_TARGET_WAIT`（**5.0s**）；此后 `_poll_join` 若在该
  时刻仍找不到**未填过**的目标，就收波。填完一个目标只把 `next_deadline`
  清回 `None`，表要等**真的开搜**才起。
  > 实现修正（2026-10-09，两轮）：原措辞是「填完第一个目标后设，此后不再
  > 重置」。改成「每填完一个都设」仍不对——**起表时刻错了**。填完那一刻起
  > 表，而状态机要过约 3 拍才回到 `_poll_join`，`WorkerRunner` 步间还有
  > `jitter(poll_interval)`（默认 2.0s，`runner.py:199`），等真去搜时 5s
  > 早已耗尽 → 整波只填得到第一个目标（**正是用户报的那条故障**）。窗口量
  > 的是**搜索时长**，所以表在「开始搜」那一刻才起。

转移表（`_setup`）改动：

```
JOIN_CHECKED --(joined=True 且 filled 未覆盖全部目标)--> NORMALIZE
JOIN_CHECKED --(全部填完 / 这一轮没填上)-------------> WAIT_LAUNCH_EVENT
FIND_JOIN    --(搜下一个目标的窗口过期 / 长窗口耗尽)--> WAIT_LAUNCH_EVENT
```

> 「窗口过期就收波」这条判据**只**挂在 `FIND_JOIN` 的放弃边上
> （`_find_join_give_up`）。原计划在 `JOIN_CHECKED` 的继续边上也判一次
> `next_deadline`——那是在**刚填成功**之后问「窗口过没过」，量的是「填完一个
> 目标花掉的时间」，与「搜索时长」是两回事，必然恒为「过期」，把每一波都
> 截在两个目标。已删除。

- `NORMALIZE` 复用现有 `_normalize_view`（关掉上一步残留的战争列表/表单），
  再走 `OPEN_WAR → FIND_JOIN`。
- `_poll_join` 跳过 `ctx["filled"]` 里的目标。
- 收波时（`_wave_done`）丢掉残留在起波窗口里的 `_pending_event`：波次模式的
  SM 跨波存活，留着它会在回到 `IDLE` 的瞬间再开一波，去填已经填过的车头
  （第一个目标走长窗口，白烧最多 3 分钟）。
- 收波时把 `current` 置回 `WAIT_LAUNCH_EVENT` 并清空 `ctx["filled"]`/`next_deadline`
  （清空动作放在 `_consume_event`，即下一波开始时；收波只切状态，便于日志观察）。
- 迭代上限：单波最多 `len(fill_targets) + 1` 次 join 尝试，防止任何 guard 漏网导致死循环。
- **第一个**目标仍用既有的长窗口（`_JOIN_MAX_ATTEMPTS=60` × `_JOIN_POLL_TIMEOUT=3s`）——
  那是「等车头开出集结」用的；5s 窗口只管**第一个之后**的剩余目标。
- `_exhausted`（长窗口耗尽仍没找到任何目标）由「置失败终态」改为**收波**
  （warning 日志 + 回 `WAIT_LAUNCH_EVENT`）。成员不记轮次，故 `no_rally_found`
  这条失败口径随之作废。

`is_terminal()` **恒返回 False**（成员不再有终态）。step 异常连败（`runner._error_streak`）
与「一台上报即全停」的既有兜底不变。

> **只改 `role == MEMBER`**。`either` 的成员阶段仍嵌在自己那台「一轮一填」的状态机里
> （它的车头阶段每轮要重来），不适用本节的波次模型。

### 2.4 收工链路

`is_terminal()` 恒假 → 成员永不自然收工 → 现有「全部 worker 都上报才发
`all_workers_done`」永不成立。改 `runtime`：

- `__init__` 记 `self._roles: dict[str, RoleEnum]`（`_spawn` 时按 `char.role` 填）。
- `_on_worker_finished`：当**所有 `leader`/`either`** 都已在 `_stopped` 里 →
  对每个未收工的 `member` runner 调 `stop(timeout=_STOP_TIMEOUT)` → 再
  `publish("all_workers_done")` 并清状态。
- 配置至少 1 个 leader/either（`config.py:118` 已保证），所以这条出口一定可达。

### 2.5 体力补充

`state_machine._refill_ap()`（`state_machine.py:147`）改为循环：领每日免费 →
反复点第二行「使用」，直到弹窗消失或**连续两次点击后弹窗状态无变化**
（判定「没道具了」）→ 返回是否关掉。`_AP_REFILL_MAX`（`leader_sm.py:54`）上调到
`8`（覆盖多次吃道具）。

> ⚠️ 待实机确认：「道具吃完」时弹窗长什么样（道具行是否消失/变灰）。当前按
> 「点击无变化」兜底，不做新模板。

## 3. P2 —— 车头多预设队列

### 3.1 配置 schema（`infra/config.py`）

```python
class MarchPreset(BaseModel):
    preset: int = Field(ge=1, le=5)
    troops: list[Literal["infantry", "cavalry", "archer"]]   # 非空

class CharacterConfig(BaseModel):
    march_presets: list[MarchPreset] = []        # 新字段，有序，1..MAX_MARCH_PRESETS 项
    march_preset: int | None = None              # 旧字段，保留兼容
    march_troop_types: list[...] = []            # 旧字段，保留兼容

    @model_validator(mode="after")
    def _migrate_march(self):
        # march_presets 为空时，由旧字段合成一条；两者都空则报错
```

- **兼容**：现有 `config.yaml`（只写 `march_preset` + `march_troop_types`）
  不改也能读；GUI 保存后写成新字段。旧字段保留为「只读兼容」，不再由 GUI 写。
- 校验：`march_presets` 非空（迁移后）、每项 `troops` 非空、预设号 1..5、
  项数 ≤ `MAX_MARCH_PRESETS = 3`（与 `MAX_TARGET_LEVELS` 同理：列表越长，
  逐个确认高亮的代价越大）。

### 3.2 车头状态机（`workers/leader_sm.py`）

- 构造参数由 `march_preset: int, march_troop_types: list` 改为
  `march_presets: list[tuple[int, list[str]]]`（`factory.py` / `either_sm.py` 同步）。
- `_select_preset()` → **返回实际选中的 `(preset, troops)`**：按列表顺序，对每个
  预设跑**现有那套**「模板点击 + 列基准自校准 + 确认 `selected_preset_N` 高亮」
  （`leader_sm.py:585` 原逻辑，逐字复用）；**第一个确认成功的胜出**。
  全部确认不了 → **仍抛异常**（保持 loud 失败）。
- `_form_troop()`：用**胜出预设自己的** `troops` 点 `troop_*`（不是全局兵种）。
- `last_rally_event["march_preset"]` 记**实际使用**的预设号（供日志/账本）。

### 3.3 队列门槛（`workers/leader_sm.py:queue_verdict` + `queue_gate.py`）

- `queue_verdict()`：把 `queue_return_icon` **移出阻塞集合**；新增返回值
  `"returning"`——判读顺序改为：
  1. `march / flag / battle / fight / recall` 任一命中 → `"battle"`（阻塞，不变）
  2. 否则 `queue_return_icon` 命中 → `"returning"`
  3. 否则 `queue_gather_icon` 命中 → `"gather"`
  4. 否则 `"unknown"`
- `QueueGate.observe()`（`queue_gate.py:94`）：`"returning"` 与 `none`/`gather`
  同样 **PROCEED**。回城账本 `mark_troops_home` **只在 `"none"` 时写**（口径不变）。

> 「返回中放行 + 强制换可用预设」由此自动成立：门槛放行 → 到创建部队面板时，
> 还在返程的那一预设确认不了高亮 → 自动落到下一个预设；都不行则抛异常重试。

## 4. P3 —— 断网弹框归一化

### 4.1 实机事实（截图 `imgs/fix/MuMu-20261009-122540-501.png`，1920×1080）

- 居中模态：标题栏「网络已断开」，正文「网络不稳定，连接已断开。请点击确定重新连接。(N)」，
  下方蓝色「**确定**」按钮。
- 「确定」按钮实测 **bbox `(779,666)-(1142,757)`**，中心 **`(960,711)`**，尺寸 363×91。
- 正文里的 `(N)` 是**重连次数**，会变 → 不能拿正文做模板。
- 弹框四周地图仍可见 → `alliance_btn`/`search_icon` 可能露出来，现有
  `_normalize_view` 会在**第一行**就 `return`，根本不会去关它。

### 4.2 设计

1. **模板**：从截图裁 `(779,666,1142,757)` 存为 `templates/net_error_confirm.png`，
   manifest 加条目（`threshold: 0.9`，`roi` 取按钮附近 `(700,620,1220,800)`）。
   阈值按仓库惯例在实机帧上校准。
2. **`ViewProbe`**（`core/recognizers/view_probe.py`）：新增 `View.NET_ERROR = "网络断开"`，
   加入 `VIEW_ANCHORS`（锚点 `net_error_confirm`），并放在 `VIEW_PRIORITY` **最前**
   （它盖住一切，必须最先判）。
3. **`_normalize_view`**（`member_sm.py:142` / `leader_sm.py:299`）：**最前面**加一段：
   命中 `net_error_confirm` → 点 `(960,711)` → 有界等待弹框消失（最多 3 次点击）→
   再走原有清理清单。点击后若地图未就绪，由原有末尾判据兜底。
4. **`queue_verdict`**：门槛判读前若命中 `net_error_confirm`，先点掉再判（否则队列栏
   被模态遮住 → 判 `unknown` → fail-closed 干等）。
